## Primary failure — Lamport “private” material is derivable from public source

Wave 96 presents deterministic Lamport one-time signatures as a limited public-verification experiment and states that checkpoint private signing material can be erased after signing while the checkpoint remains verifiable.

However, `lpair()` constructs every private Lamport preimage as:

```python
sha256(f"w96|{root}|{generation}|{index}|{bit}")
```

There is no secret seed or entropy. `root`, `generation`, `index`, `bit`, and the derivation recipe are all public. The `predecessor_pub_sha` affects the public-key object hash but not the private preimages.

Therefore the supposed private material can be regenerated by anyone with the published source. The in-memory `priv` dictionary is not a secrecy boundary.

### Exact-API reproduction

`verification/wave96_deterministic_lamport_forgery_repro.py` performs this sequence:

1. Create/commit/externally-anchor a normal checkpoint 1 and confirm `AUTHORITATIVE_PUBLIC_CHECKPOINTED`.
2. Advance state normally and call the normal `prep()` for checkpoint 2. This signs checkpoint 2 and marks its Lamport signer hashes in Wave 96's normal `used` set.
3. Delete every retained checkpoint-2 signer entry from the builder's `private_store`.
4. Reconstruct the exact same Lamport private rows from each signer's public `root`, `generation`, and `predecessor_pub_sha` using the published `lpair()` routine.
5. Sign a *different sibling checkpoint 2* with the already-used signer set.
6. Give that sibling intentionally nonexistent `next_signer_keys` to make the divergent checkpoint observably different and to test successor-key validation.
7. The unchanged Wave 96 `verifycp()` accepts the second signature under the already-used OTS keys.
8. The unchanged `applycp()` returns `COMMITTED`.
9. The unchanged modeled external `extpub()` returns `APPENDED`.
10. The unchanged `auth()` returns `AUTHORITATIVE_PUBLIC_CHECKPOINTED`.
11. Only when checkpoint 3 is later prepared does the poisoned successor set finally fail with `pub_sha body missing`.

Expected verifier verdict:

`FAIL_DETERMINISTIC_LAMPORT_PRIVATE_MATERIAL_IS_PUBLICLY_REGENERABLE`

This is stronger than ordinary OTS signer reuse by a holder of retained secret state: the verifier first deletes the modeled retained private material and then reconstructs it from public information.

## Secondary semantic boundary exposed by the same reproduction

`verifycp()` validates the *current* signer set, predecessor, epoch, and signatures, but it does not resolve or validate the checkpoint's `next_signer_keys` before the checkpoint becomes authoritative. A signed checkpoint can therefore become current while pointing at nonexistent successor signer bodies. The failure is deferred until the next checkpoint attempt.

This is not the primary cryptographic failure, but it makes the accepted forged checkpoint capable of poisoning future checkpoint progress while still being reported authoritative now.

## Benchmark / extrapolation check

No fresh monolith workload is involved in Wave 96. The published ~6–13 ms numbers are synthetic single-host process-CPU costs for checkpoint construction/public verification. They do not support claims about retained-state wins, incremental wins, dormant compute, joules, remote latency, or distributed consensus. ## Bounded conclusion

Wave 96 improves monotonic checkpoint lineage and repeat compaction, but its public-verification authority claim does **not** yet establish possession of secret one-time signing material. The test Lamport private material is deterministic public data in disguise, and the same signer generation can be recreated and used to produce a competing checkpoint after the normal path already consumed it.
